### 1. Core Anaplan Object Model

Anaplan organizes data and logic in a hierarchical structure, moving from broad containers to granular data points.

*   **Workspace**:
    *   The highest-level container in Anaplan.
    *   A secure environment where one or more **Models** reside.
    *   Analogy: Think of a Workspace as a complete, self-contained business analytics environment, similar to a database server instance.
*   **Model**:
    *   A self-contained application designed for a specific business process or subject area (e.g., Financial Planning, Sales Forecasting).
    *   Comprises **Modules**, **Lists**, **Line Items**, **Time**, and **Versions**.
    *   Analogy: A Model is akin to a specific data warehouse or a star schema environment dedicated to a particular business function.
*   **Modules**:
    *   The primary building blocks for data storage and calculation within a Model.
    *   Each module holds specific data points (**Line Items**) and is dimensioned by a selection of **Lists** and built-in dimensions (Time, Versions).
    *   **Types of Modules:**
        *   **Data Modules**: Store input data or calculated results, often serving as fact tables.
        *   **System Modules**: Store metadata, properties of lists, assumptions, or lookups. They typically have fewer dimensions and contain line items used for global settings or properties.
    *   Analogy: Modules are analogous to **fact tables** (for data) or **helper tables** (for system configurations) in a dimensional model.
*   **Lists**:
    *   Define the dimensions of your model, representing business entities (e.g., Products, Departments, Customers, GL Accounts).
    *   Lists can be:
        *   **Flat**: A simple, non-hierarchical list.
        *   **Hierarchical**: Contains parent-child relationships, enabling roll-ups and drill-downs.
        *   **Numbered**: Lists where each item has a unique numeric ID, often used for transactional details or scenarios where unique instances are needed (e.g., project IDs, invoice numbers).
    *   Analogy: Lists are directly comparable to **dimension tables** in dimensional modeling.
*   **Line Items**:
    *   The individual data points or calculation fields within a **Module**.
    *   Each Line Item has a data type (e.g., Number, Boolean, Date, Text, List-formatted, Time-formatted) and specific properties (e.g., summary method, formula).
    *   Analogy: Numeric Line Items are equivalent to **measures** (facts) in a fact table. Text, Boolean, Date, and List-formatted Line Items are equivalent to **attributes** within a fact table or attributes derived from dimension tables.
*   **Time**:
    *   A built-in, configurable dimension crucial for time-series data and planning.
    *   Can be set to various granularities (e.g., Year, Quarter, Month, Week, Day).
    *   Analogy: The Time dimension.
*   **Versions**:
    *   A built-in dimension used to differentiate scenarios (e.g., Actual, Budget, Forecast, Scenario A).
    *   Analogy: A specific type of dimension, often implemented in data warehouses for scenario analysis.

### 2. Anaplan's Architecture Mapping to Dimensional Modeling

Anaplan's design principles naturally align with dimensional modeling, offering a familiar structure for CPAs and data architects.

*   **Modules as Fact Tables**:
    *   **Definition**: In dimensional modeling, a fact table stores quantitative measures at the intersection of various business dimensions.
    *   **Anaplan Mapping**: An Anaplan **Module** serves as a fact table. It is explicitly dimensioned by the **Lists** selected in its blueprint, and contains **Line Items** that represent the measures and attributes relevant to that specific combination of dimensions.
    *   **Example**: A `Sales Data` module dimensioned by `Products`, `Customers`, and `Time` would store `Sales Amount` and `Quantity Sold` (Line Items/measures) for each specific product, customer, and time period combination. This is a direct parallel to a `Sales Fact` table.

*   **Lists as Dimension Tables**:
    *   **Definition**: Dimension tables contain descriptive attributes about the business entities (e.g., Product Name, Customer Region, GL Account Hierarchy).
    *   **Anaplan Mapping**: An Anaplan **List** functions as a dimension table. Each item in the list represents a unique member of that dimension (e.g., "Laptop Pro" in the `Products` list). List properties (often stored in system modules) act as attributes of these dimension members.
    *   **Example**: A `Products` list (dimension table) can have properties like `Product Category`, `Brand`, and `Unit Cost` (attributes) associated with each product item. These properties are typically stored as Line Items in a dedicated system module, dimensioned by the `Products` list.

*   **Line Items as Measures / Attributes**:
    *   **Definition**:
        *   **Measures**: Quantitative, numerical facts that are aggregated (e.g., Sales Revenue, Headcount, Spend).
        *   **Attributes**: Descriptive characteristics of a fact or dimension member (e.g., Product Name, Department Manager, Date).
    *   **Anaplan Mapping**:
        *   **Measures**: Numeric **Line Items** in a module (e.g., `Sales Amount`, `Units Sold`, `Budgeted Cost`).
        *   **Attributes**: Text, Boolean, Date, or List-formatted **Line Items**. For example, a `Product Type` Line Item (formatted as a list, referencing the `Product Types` list) within a sales module acts as an attribute, allowing you to categorize sales by product type. Similarly, Line Items in system modules that define properties of List items (e.g., `Product.Category` as a Line Item in a `Product Properties` module) function as dimension attributes.

### 3. Formula Syntax Basics

Anaplan formulas are intuitive and operate based on the context of the module and line items they reference.

*   **General Principles**:
    *   Formulas are case-insensitive.
    *   Line items are referenced by their name.
    *   Formulas evaluate based on the dimensions applied to the module they reside in.
    *   Anaplan automatically handles implicit aggregation where dimensions differ, often requiring explicit `SUM` or `LOOKUP` for clarity and control.

*   **Referencing Line Items**:
    *   **Within the same module**: Simply use the line item name.
        ```
        'Gross Profit' = 'Sales Revenue' - 'Cost of Goods Sold'
        ```
    *   **From another module**: Use `Module Name.Line Item Name`.
        ```
        'Allocated Expenses' = 'SYS03 Corp Expenses.Total Corporate Expenses'
        ```
    *   **Referencing a list property (via a system module)**:
        ```
        'Product Cost' = 'SYS01 Product Properties.Cost per Unit'
        ```
        (Assuming `SYS01 Product Properties` module is dimensioned by `Products` list, and `Cost per Unit` is a line item within it.)

*   **SUM**: Aggregates data across a specified list or implicitly aggregates to the module's dimensionality.
    *   **Explicit Syntax**: `Line Item[SUM: List_to_Aggregate_Across]`
    *   **Function**: When a formula references a line item from a source module that has more dimensions than the target module, `SUM` aggregates the data from the source to match the target's dimensionality.
    *   **Example 1 (Explicit Aggregation)**: Calculate total sales revenue for each product across all regions.
        *   Source module: `Sales Data` (Dimensions: `Products`, `Regions`, `Time`) with Line Item `Sales Amount`.
        *   Target module: `Product Sales Summary` (Dimensions: `Products`, `Time`) with Line Item `Total Product Sales`.
        ```
        'Total Product Sales' = 'Sales Data'.'Sales Amount'[SUM: Regions]
        ```
    *   **Example 2 (Implicit Aggregation)**: If the target module `Product Sales Summary` was only dimensioned by `Products`, referencing `'Sales Data'.'Sales Amount'` directly might implicitly sum across time and regions. Explicit `SUM` is often preferred for clarity.

*   **LOOKUP**: Retrieves a specific value from another module based on a matching dimension. Essential for pulling master data or properties.
    *   **Syntax**: `Line Item [LOOKUP: Matching_Dimension_Item]` or `Source_Module.Line_Item[LOOKUP: Matching_Dimension_Item]`
    *   **Function**: Used when you need to bring a value (e.g., a cost, a manager's name, a category) from one module (or system module acting as a dimension table with attributes) into another, using a common dimension to link them.
    *   **Example**: Retrieve the `Product Category` for each `Product` in a `Sales Data` module.
        *   `SYS01 Product Properties` module: Dimensions `Products`, Line Item `Product Category` (List-formatted).
        *   `Sales Data` module: Dimensions `Products`, `Customers`, `Time`. Create a Line Item `Category Lookup`.
        ```
        'Category Lookup' = 'SYS01 Product Properties'.'Product Category'[LOOKUP: Products]
        ```
        *   Here, `Products` is the shared dimension that allows the lookup.

*   **IF**: Implements conditional logic.
    *   **Syntax**: `IF condition THEN true_value ELSE false_value`
    *   **Example**: Calculate a bonus based on sales performance.
        ```
        'Bonus Amount' = IF 'Sales Performance' > 1.1 THEN 'Base Salary' * 0.1 ELSE 0
        ```

*   **TIMESUM**: Aggregates data over specific time periods (Year-to-Date, Quarter-to-Date, rolling averages).
    *   **Syntax**: `TIMESUM(Line Item, Start Period, End Period, Aggregation Type)`
    *   **Aggregation Types**: `SUM`, `AVERAGE`, `FIRSTNONBLANK`, `LASTNONBLANK`, `MIN`, `MAX`.
    *   **Example 1 (Year-to-Date Sales)**:
        ```
        'YTD Sales' = TIMESUM('Sales Revenue', 'Current Period'.Year.Start, 'Current Period', SUM)
        ```
    *   **Example 2 (Rolling 3-Month Average Cost)**:
        ```
        'Rolling 3 Month Avg Cost' = TIMESUM('Monthly Cost', OFFSET('Current Period', -2), 'Current Period', AVERAGE)
        ```
    *   **Note**: `'Current Period'` is a frequently used time reference, representing the current cell's time period.

### 4. Best Practices for Model Design

Adhering to best practices ensures models are performant, maintainable, and scalable.

*   **D.I.S.C.O. Methodology**:
    *   A common framework for organizing modules within an Anaplan model.
    *   **D**ata: Modules holding raw, uncalculated data (inputs).
    *   **I**nput: Modules where users enter data or assumptions.
    *   **S**ystem: Modules containing master data, list properties, global constants, and time/version settings.
    *   **C**alculation: Modules performing complex calculations, often pulling data from Input/Data modules.
    *   **O**utput: Modules summarizing data for reporting, dashboards, or exports.
    *   **Benefit**: Improves navigation, performance, and maintainability by segregating different functions.

*   **Flat vs. Hierarchical Lists**:
    *   **Flat Lists**:
        *   **Use when**: No parent-child relationships are needed for aggregation or roll-ups. Suitable for properties (e.g., Product Colors) or simple categories.
        *   **Benefit**: Simpler structure, slightly faster processing for lookups if no hierarchy is required.
    *   **Hierarchical Lists**:
        *   **Use when**: Roll-ups, aggregations, and drilling down through different levels are essential (e.g., Organizational Structure, GL Accounts, Product Categories).
        *   **Benefit**: Enables powerful summarization and navigation, critical for financial reporting and planning.

*   **Module Granularity**:
    *   Design modules at the lowest necessary grain for calculations and inputs, but no lower.
    *   **Avoid over-dimensioning**: Only include dimensions (Lists, Time, Versions) in a module if the Line Items within it genuinely vary across those dimensions. Excessive dimensions can lead to sparsity and performance issues.
    *   **Example**: A `Sales Plan` module might need to be dimensioned by `Products`, `Customers`, `Time`, and `Versions`. However, a `Product Cost` module might only need `Products` and `Time` if costs don't vary by `Customer`.
    *   **Benefit**: Optimizes model size, calculation speed, and user experience.

*   **Avoiding Circular References**:
    *   Anaplan prevents direct circular references within a single line item or immediate cross-module dependencies.
    *   **Indirect Circularity**: Can occur across multiple modules (e.g., Module A calculates B, Module B calculates C, Module C calculates A).
    *   **Prevention**: Carefully design the flow of calculations. If you encounter a circular reference, break the dependency by:
        *   Introducing an intermediate calculation module.
        *   Re-evaluating the logical flow to ensure a unidirectional data flow.
    *   **Benefit**: Ensures model stability and prevents infinite loops, which can lead to calculation errors or performance degradation.

*   **CALM Methodology**:
    *   **C**onsistent: Apply consistent naming conventions, formula structures, and module layouts.
    *   **A**ccessible: Design for ease of use and understanding by end-users. Clear UI, intuitive navigation.
    *   **L**ogical: Ensure calculations flow logically and accurately reflect business processes.
    *   **M**odular: Break down complex problems into smaller, manageable modules that can be built and maintained independently.
    *   **Benefit**: Enhances collaboration, simplifies maintenance, and improves overall model quality.

*   **Naming Conventions**:
    *   Implement clear and consistent naming conventions for **Workspaces**, **Models**, **Modules**, **Lists**, **Line Items**, and **Actions**.
    *   **Example**:
        *   `MOD_Finance_Budget` (Module)
        *   `LIST_Products` (List)
        *   `LI_Revenue_Actual` (Line Item)
        *   `SYS01_Time Settings` (System Module)
    *   **Benefit**: Improves readability, navigability, and reduces errors, especially in large models.

### 5. Common Design Patterns

Anaplan models often follow repeatable patterns to address common business planning challenges.

*   **Allocation Models**:
    *   **Purpose**: Distribute a high-level budget, cost, or revenue down to a more granular level based on specific drivers.
    *   **Pattern**:
        1.  **High-Level Input Module**: Captures data at an aggregated level (e.g., total corporate overhead).
        2.  **Driver Module**: Calculates allocation percentages or units (e.g., headcount by department, square footage, revenue share). This module is dimensioned by both the source and target dimensions.
        3.  **Allocation Module**: Applies the drivers to the high-level input to distribute the value to the detailed level.
    *   **Example**: Allocate `Total Marketing Budget` (input at company level) to individual `Products` based on each product's `Forecasted Revenue Share` (driver).

*   **Driver-Based Planning**:
    *   **Purpose**: Forecast outcomes by modeling key business drivers rather than directly forecasting the outcome itself.
    *   **Pattern**:
        1.  **Driver Input Module**: Capture assumptions for key business drivers (e.g., `Units Sold`, `Average Selling Price`, `Conversion Rate`).
        2.  **Calculation Module**: Use the drivers in formulas to calculate dependent outcomes (e.g., `Revenue`, `Marketing Spend`, `Headcount`).
    *   **Example**: Forecast `Revenue` by modeling `Units Sold` (driver) and `Average Selling Price` (driver) and calculating `Revenue = Units Sold * Average Selling Price`.

*   **Rolling Forecasts**:
    *   **Purpose**: Continuously update forecasts by dropping past actuals and extending the forecast horizon forward.
    *   **Pattern**:
        1.  **Fixed Horizon**: Define a consistent forecast window (e.g., 12 months, 4 quarters).
        2.  **Actuals Integration**: Integrate actual data for past periods within the horizon.
        3.  **Forecast Extension**: As time progresses, actuals replace the earliest forecast periods, and new forecast periods are added at the end of the horizon to maintain a constant window.
    *   **Example**: A 12-month rolling forecast. In March, actuals for January-February are used. March-December are forecasted. In April, actuals for March are incorporated, and the forecast now covers April-March of the following year. This is often managed through the `Versions` dimension and careful formula logic.

*   **Data Hubs**:
    *   **Purpose**: Centralize master data, key assumptions, and common calculations to feed multiple "spoke" models. Promotes consistency and reduces data redundancy.
    *   **Pattern**:
        1.  **Hub Model**: A dedicated Anaplan model containing all master lists (e.g., `Products`, `GL Accounts`, `Employees`) and their properties, as well as global assumptions or shared calculation logic.
        2.  **Spoke Models**: Other Anaplan models (e.g., `Sales Planning`, `HR Planning`, `Financial Reporting`) that import the necessary lists and data from the Hub Model.
    *   **Benefit**: Ensures a single source of truth for critical data, simplifies maintenance across an Anaplan ecosystem, and optimizes performance by offloading master data management.

## **1. Core Object Model**
Anaplan’s architecture is built around a **dimensional modeling** approach, where objects are structured hierarchically to enable scalable, multi-dimensional planning.

### **1.1 Workspaces**
- **Definition**: A container for related models (e.g., "Finance Planning," "Sales Forecasting").
- **Key Properties**:
  - Access-controlled (user/role permissions).
  - Can host multiple models.

### **1.2 Models**
- **Definition**: A self-contained planning environment (e.g., "Budget 2024," "Headcount Planning").
- **Key Properties**:
  - Contains modules, lists, and line items.
  - Can be linked to other models via imports/exports.

### **1.3 Lists (Dimension Tables)**
- **Definition**: A collection of unique items (e.g., "Products," "Regions," "Time").
- **Types**:
  - **Flat**: Simple lists (e.g., "Product Codes").
  - **Hierarchical**: Parent-child relationships (e.g., "Region → Country → City").
  - **Numbered**: Auto-generated IDs (e.g., "Employee IDs").

### **1.4 Modules (Fact Tables)**
- **Definition**: A grid of data structured by dimensions (lists) and measures (line items).
- **Key Properties**:
  - **Dimensions**: Lists applied to the module (e.g., "Time," "Product").
  - **Line Items**: Measures/attributes (e.g., "Revenue," "Cost").

### **1.5 Line Items (Measures/Attributes)**
- **Definition**: The data fields in a module (e.g., "Sales," "Headcount").
- **Types**:
  - **Number**: Numeric values (e.g., "Revenue").
  - **Text**: Descriptive fields (e.g., "Comments").
  - **Boolean**: True/False flags (e.g., "Is Active?").

### **1.6 Relationships**
- **Lists → Modules**: Modules are "sliced" by lists (e.g., a "Sales" module may use "Time" and "Product" lists).
- **Line Items → Other Line Items**: Formulas reference other line items (e.g., `Revenue = Price * Quantity`).

## **3. Formula Syntax Basics**
Anaplan uses a **spreadsheet-like** formula language with dimensional awareness.

### **3.1 Common Functions**
| **Function**       | **Purpose**                          | **Example**                          |
|--------------------|-------------------------------------|------------------------------------|
| `SUM`             | Aggregates values across dimensions | `SUM(Revenue)`                     |
| `LOOKUP`          | Retrieves data from another module | `LOOKUP(Price, Product, SKU)`      |
| `IF`              | Conditional logic                   | `IF(Revenue > 1000, "High", "Low")` |
| `TIMESUM`         | Aggregates over time periods        | `TIMESUM(Revenue, Month, Year)`     |

### **3.2 Line Item References**
- **Same Module**: `Revenue = Price * Quantity`
- **Cross-Module**: `LOOKUP(Price, Product, SKU)`

## **4. Best Practices for Model Design**
### **4.1 Lists: Flat vs. Hierarchical**
- **Flat Lists**: Use for simple, non-hierarchical data (e.g., "Employee IDs").
- **Hierarchical Lists**: Use for rollups (e.g., "Region → Country → City").

### **4.2 Module Granularity**
- **Avoid Over-Granularity**: Too many modules increase complexity.
- **Use Submodules**: For logical separation (e.g., "Sales" vs. "Costs").

### **4.3 Avoiding Circular References**
- **Rule**: Never have a line item reference itself directly or indirectly.
- **Example of Bad Design**:
  - `A = B + 1`
  - `B = A - 1`
  - **Fix**: Restructure to remove dependency loops.

## **5. Common Design Patterns**
### **5.1 Allocation Models**
- **Use Case**: Distributing costs/revenue across dimensions (e.g., "Allocate Corporate Overhead to Departments").
- **Implementation**:
  - Use `LOOKUP` to reference allocation rules.
  - Apply `SUM` to aggregate results.

### **5.2 Driver-Based Planning**
- **Use Case**: Forecasting based on key drivers (e.g., "Sales = Price * Volume").
- **Implementation**:
  - Define drivers as line items.
  - Use formulas to link them (e.g., `Revenue = Price * Units Sold`).

### **5.3 Rolling Forecasts**
- **Use Case**: Dynamic forecasting (e.g., "12-month rolling budget").
- **Implementation**:
  - Use `TIMESUM` to aggregate over rolling periods.
  - Automate updates via imports.
